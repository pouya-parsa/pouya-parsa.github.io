Can the Cloud Drive?

Infrastructure feasibility of offloading autonomous driving across 5G and 6G.

Pouya Parsa, Kawon Han, and Seongjin Choi

The short answer

Can autonomous-driving inference move to the cloud?

Yes—but only conditionally, and in a specific order. In dense cities, the uplink must carry the offloaded workload first. The cloud must then return a decision within either a 100 ms reactive loop or a 300 ms deliberative tier backed by a local reactive controller. Only after both gates pass does shared cloud compute become an economic question.

Core finding

Latency decides which model is admissible in which year; cost decides whether it is economical.

The result in one sequence

Three constraints bind—one after another.

The paper links a driving-model split, the cellular access network, and cloud GPU service into one deployment question. A branch must clear each gate before the next one matters.

Gate 01 Communication-bound

Dense cells run out of uplink first.

Cloud driving reverses normal mobile traffic: the difficult flow is upstream. Raw sensors require 100 Mbps per vehicle, compressed features 25 Mbps, and compact queries 3 Mbps. As more vehicles share a cell, bandwidth is divided and interference lowers spectral efficiency.

At the NYC reference point—10% AV penetration and 45% utilization—plain 5G already fails feature-level offloading. 5G-Advanced is the practical threshold; 6G adds headroom.

Gate 02 Compute-bound

More bandwidth cannot outrun a memory wall.

On 2025 hardware, the deterministic vision-language-action (VLA) floor is 132–164 ms before network or queueing delay. Autoregressive decode alone is about 114 ms because each generated token rereads model weights from high-bandwidth memory (HBM).

The floor first clears 100 ms around 2027. After access-network tails are added, 6G admits dense VLA-S2 around 2028; 5G-Advanced does not clear the same reactive corridor.

Gate 03 Cost-bound

Only feasible branches earn a cost comparison.

Onboard hardware is purchased for every vehicle, even when it is parked. Cloud GPUs are pooled across vehicles that are active at the same moment. This asymmetry matters most for VLA hardware, whose reference baseline reaches $8,500 per vehicle-year.

Once admissible, low- and moderate-utilization VLA fleets gain the most. Feature-level offloading (S2) is where the cost advantage concentrates.

Where should the pipeline split?

Three offloading strategies trade bandwidth for onboard compute.

S1 Raw sensor

Most cloud, most uplink

100 Mbps

Uploads camera, LiDAR, and radar streams. It leaves only encoding onboard, but dense cells reach the communication cliff early.

S2 Feature level

The robust middle

25 Mbps

Keeps the vision backbone local and offloads compressed features. This is where VLA feasibility and the cost crossover concentrate.

S3 Query level

Least uplink, most onboard

3 Mbps

Uploads compact scene queries after the transformer encoder. It is easiest on the network but preserves much of the vehicle hardware cost.

Five findings to carry forward.

    Plain 5G loses feature-level headroom at the dense NYC reference point; 6G supports broader adoption.

    The FP16 autoregressive decode is limited by HBM bandwidth, regardless of radio bandwidth.

    Cloud pooling is most valuable when expensive peak hardware would otherwise sit idle in every vehicle.

  5. 05
    S2 is the robust middle—not a universal optimum.

    It avoids S1’s uplink extreme and S3’s residual-hardware extreme across much of the study grid.

Read the boundary conditions

What this analysis does not claim.

Not a safety case

Every cloud-dependent architecture adds outage, edge-site, and latency-spike failure modes. A deliberative result never removes the need for local reactive control.

6G values are targets

The 6G parameters use ITU IMT-2030 aspirations, not guaranteed deployed performance.

Architecture can shift the wall

FP8, speculative decoding, distillation, or parallel action decoders could move the VLA timing boundary earlier.

NYC averages hide hotspots

Rush-hour corridors may see several times the average cell load even when a citywide scenario appears feasible.

Costs are analytical estimates

Energy is excluded and marginal cost crossovers could move later. The simulator explains the paper’s assumptions; it does not rerun a live infrastructure bid.

Frequently asked questions

Quick answers about cloud driving.

Can the cloud drive an autonomous vehicle?

Conditionally. The selected offloading strategy must first fit the cellular uplink, then satisfy the closed-loop latency budget. Only a branch that passes both gates should be compared economically with full onboard compute.

Why doesn’t faster 6G solve the whole problem?

More bandwidth cannot remove the memory-bandwidth-bound autoregressive decode time of a vision-language-action model. In the paper, communication, compute latency, and cost bind in sequence.

What is feature-level offloading, or S2?

S2 keeps the vision backbone in the vehicle and uploads compressed intermediate features. It uses much less uplink than raw-sensor offloading while moving more expensive reasoning and planning work to shared infrastructure.

What is the difference between the 100 ms and 300 ms tiers?

The 100 ms tier is the reactive control loop. The 300 ms tier is deliberative planning and is admissible only behind an onboard reactive controller that can act locally within 100 ms.

Is this simulator a deployment or safety-certification tool?

No. It is an interactive explainer of the analytical assumptions and discrete scenario space published in arXiv:2607.09045v1.
